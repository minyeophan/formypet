# AI 작업 흐름

이 문서는 복잡한 리팩터링, 다단계 구현, 문서 체계 정리, Handover 작성이 필요한 작업에서만 읽는다.

## 작업 판단 원칙

- 먼저 사용자 요청의 성공 조건을 한 문장으로 정리한다.
- 요청이 모호하면 가능한 해석을 나열하고, 위험한 추측은 하지 않는다.
- 더 단순한 방법이 있으면 구현 전에 말한다.
- 현재 코드와 문서 구조를 읽은 뒤 기존 패턴을 따른다.
- 작업 범위 밖의 문제는 발견해도 고치지 말고 최종 보고에만 남긴다.

## 계획 원칙

- 다단계 작업은 짧은 계획을 만든다.
- 각 단계는 하나의 Verify 조건을 가진다.
- Verify가 불명확하면 시작 전에 다시 쓴다.
- 한 단계가 깨진 상태로 다음 단계에 넘어가지 않는다.
- 계획 파일이 있다면 계획을 우선하되, 현재 파일 상태와 충돌하면 사용자에게 알린다.

예시:

```text
1. 문서 구조 확인 -> verify: 삭제 대상 참조 검색
2. 라우터 문서 축소 -> verify: AGENTS.md 줄 수와 조건부 링크 확인
3. 검증 실행 -> verify: 한글 깨짐 검사와 변경 범위 확인
```

## 변경 원칙

- 최소 변경으로 목표를 달성한다.
- 단일 사용처를 위해 새 추상화를 만들지 않는다.
- 기존 스타일과 용어를 따른다.
- 요청 범위와 무관한 포맷팅을 하지 않는다.
- 내가 만든 변경 때문에 생긴 orphan만 정리한다.
- 문서 이동은 중복을 줄이는 방향으로 한다.
- 오래된 상태 문구는 현재 기준으로 바꾸거나, 역사 설명이면 현재 기준이 아님을 명시한다.

## 검증 원칙

- 검증 명령은 계획에 있는 것을 우선 실행한다.
- 실패하면 원인을 좁히고, 같은 실패를 반복하지 않게 수정한다.
- 한글 문서 편집 뒤에는 한글 깨짐 검사를 실행한다.
- 삭제 작업 뒤에는 역참조 검색을 실행한다.
- 문서 크기를 줄이는 작업은 줄 수 또는 파일 크기를 확인한다.
- 애플리케이션 코드를 건드리지 않는 작업이면 `git status --short backend frontend DESIGN.md`로 범위 이탈을 확인한다.

## Phase 규칙

- 각 Phase는 하나의 명확한 Verify 조건을 가진다.
- Verify가 통과하기 전에는 다음 Phase를 시작하지 않는다.
- Phase 완료 이력은 세부 task 파일 대신 요약 문서에 남긴다.
- 완료된 계획 파일은 현재 작업에 필요하지 않으면 제거한다.
- Phase가 배포, 클라우드, 외부 서비스와 연결될 때는 재진입 조건을 따로 적는다.

## Handover 규칙

세션 종료 또는 큰 작업 단위 완료 시 `docs/CONTEXT.md`의 최신 Handover만 갱신한다. 오래된 Handover를 계속 누적하지 않는다.

Handover에는 다음 항목을 포함한다.

- Goal: 이번 세션의 목표
- Done: 실제 완료한 작업
- Remaining: 남은 일과 끝내지 못한 이유
- Next step: 다음 작업자가 처음 실행할 구체적 행동
- Warnings: 건드리면 안 되는 파일, 알려진 위험, 임시 조치

## 중단 기준

- 사용자 요청과 기존 상태가 정면으로 충돌한다.
- 삭제 대상이 현재 코드나 문서에서 여전히 참조된다.
- 계획 범위 밖의 코드 변경이 새로 발생했다.
- 검증 실패 원인을 합리적으로 좁힐 수 없다.
- 인코딩 손상이 의심되는데 원본 내용을 복구할 수 없다.
