# 02. 도메인 결정표

> 상태: 확정

> 선행 문서: `docs/BACKEND_INVENTORY.md`

## 목적

백엔드 전체 도메인의 현재 상태와 처리 방향을 정한다. 이 단계에서는 세부 테이블명, API 경로, 클래스명까지 확정하지 않고, 각 도메인을 `유지`, `수정 필요`, `신규 구현`, `프론트만 있음`, `죽은 코드 후보`, `보류` 중 어디에 둘지 결정한다.

## 전체 결정 원칙

- 사용자 화면 이름, 백엔드 도메인, DB 저장 단위는 필요하면 분리해서 판단한다.
- 현재 프론트 route가 있더라도 백엔드 계약이 없으면 `프론트만 있음` 또는 `보류`로 둔다.
- 구현할 도메인은 3~7번 문서에서 ERD, API, migration, 구현, 테스트 계획을 순서대로 확정한 뒤 시작한다.
- 확정되지 않은 이름을 다음 문서에서 확정처럼 쓰지 않는다.
- 죽은 코드 후보는 대체 기능 연결 전에는 삭제하지 않는다.

## 결정 상태 기준

| 결정 | 의미 |
|------|------|
| 유지 | 현재 백엔드 API, 테이블, 테스트, 프론트 호출이 대체로 맞물려 있어 회귀 방지만 필요하다. |
| 수정 필요 | 기능은 있으나 프론트 연결, 도메인 경계, 표시, 저장 흐름 중 보강이나 정리가 필요하다. |
| 신규 구현 | 사용자 동선 또는 프론트 화면은 있으나 백엔드 API/테이블/테스트가 없어 새 구현이 필요하다. |
| 프론트만 있음 | 프론트 화면이나 route는 있지만 이번 단계에서 신규 구현으로 확정하지 않은 상태다. |
| 죽은 코드 후보 | 대체 기능 연결 뒤 사용처 검색을 거쳐 제거할 수 있는 레거시 흔적이다. |
| 보류 | 이번 백엔드 정비 범위에서 구현하지 않고 별도 결정으로 넘긴다. |

## 우선순위 기준

| 우선순위 | 의미 |
|----------|------|
| 높음 | 현재 사용자 동선이 깨져 있거나, 다음 구현/정리 대상 후보로 3~10번 단계에 직접 영향을 준다. |
| 중간 | 기능은 있으나 연결, 표시, 수정 흐름이 약해 후속 보강 여부를 결정해야 한다. |
| 낮음 | 현재 유지가 우선이며 이번 범위에서는 회귀 방지와 기존 계약 보존이 핵심이다. |

## 이번 단계에서 특히 신경 쓸 부분

- 지갑은 신규 구현 대상이지만, 2번 문서에서 테이블명과 API 경로를 확정하지 않는다.
- 지갑은 사용자가 홈의 지갑에서 자신의 반려동물별 지출 내역을 저장하고 조회하는 기능이다.
- `expense`라는 개념 자체를 금지하지 않는다. 금지 대상은 기록 도메인의 `record expense`다.
- 지출은 기록 도메인의 타입으로 되살리지 않는다.
- `/records/expense/new`와 `ActivityRecord` 기반 지출 저장/파싱 흔적은 제거 후보지만, 실제 제거는 10번 단계에서 검색 후 진행한다.
- 일정은 UI가 있어도 이번 백엔드 정비 범위에서는 보류로 둔다.
- 루틴, 커뮤니티, 사용자 프로필은 이미 백엔드가 있으므로 신규 구현보다 연결/보강 여부 판단이 중요하다.

## 지갑과 기록 expense 경계

| 구분 | 결정 |
|------|------|
| 홈의 `/wallet` 진입 | 유지 |
| 지갑 도메인의 지출 개념 | 허용 |
| 반려동물별 지출 저장/조회 | 신규 구현 |
| `activity_records.type_id = 'expense'` | 금지 |
| 기록 입력 화면의 expense 타입 | 금지 |
| `/records/expense/new` 신규 진입점 사용 | 금지 |
| `ActivityRecord` 기반 expense 저장/파싱 | 제거 후보 |

정리: 지갑은 반려동물별 지출 내역을 다루는 신규 도메인이다. 기록 도메인의 `expense` 타입은 사용하지 않는다. `expense`라는 개념은 지갑 도메인 안의 지출 리소스로만 허용한다.

## 3번 ERD로 넘길 대상

| 대상 | 처리 |
|------|------|
| 지갑 | 신규 구현 대상이다. 3번에서 신규 테이블 필요 여부, 테이블명, 필드, FK, index, nullable 정책을 결정한다. |
| 미디어 | 기존 도메인은 유지한다. 지갑 영수증 같은 신규 첨부는 3번에서 1차 범위인지 2차 후보인지 따로 결정한다. |
| 기록 | 기존 테이블은 유지한다. `record expense`를 위해 `activity_records`나 activity type을 확장하지 않는다. |
| 일정 | 보류 상태이므로 3번 ERD에서 신규 테이블을 만들지 않는다. |

## 10번 지갑 cleanup으로 넘길 대상

| 후보 | 처리 |
|------|------|
| `/records/expense/new` | 지갑 대체 흐름 연결 뒤 사용처 검색 후 제거 여부를 결정한다. |
| `ActivityRecord` 기반 expense 저장/파싱 | 지갑 대체 흐름 연결 뒤 제거 후보로 추적한다. |

## 별도 기록 cleanup 후보

| 후보 | 처리 |
|------|------|
| `bath`, `groom` 레거시 흔적 | 지갑 지출과 직접 관련이 없으므로 10번 지갑 cleanup에 넣지 않고, 별도 기록 cleanup 후보로 남긴다. |

## 이번 단계에서 결정하지 않는 것

- 신규 테이블의 정확한 필드, FK, index
- API endpoint와 request/response 필드
- Flyway 파일 번호와 SQL
- Java 패키지, 클래스, DTO 이름
- 프론트 파일명과 provider/service 구조
- 죽은 코드 실제 삭제 목록
