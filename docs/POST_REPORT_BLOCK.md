# 게시글 신고·작성자 차단

작업 브랜치: `feat/post-report-block`

## 이번 구현 범위

- 다른 사용자의 게시글 더보기에서 신고하기·작성자 차단으로 진입한다. 본인 글은 기존 수정·삭제 메뉴를 유지한다.
- 신고 사유는 광고/스팸, 욕설/괴롭힘, 부적절한 내용, 개인정보 노출, 기타다. 선택한 동그라미는 기존 브랜드 초록색 `#32B982`다.
- 상세 내용은 최대 500자이며 기타 사유일 때 필수다. 서버가 접수번호·접수 시각을 반환해야 성공 화면을 표시한다.
- 실패하면 사유·입력 내용을 유지하고 재시도한다. 동일한 내용의 재시도는 같은 `requestId`를 사용하며, 전송 중에는 중복 제출과 화면 닫기를 막는다.
- 작성자 차단과 차단 해제는 확인 창을 거친다. 요청 실패 시 창과 기존 목록을 유지한다.
- 기존 마이페이지 설정 그룹과 일반 설정 화면에 차단 목록 메뉴를 추가했다. 기존 화면의 나머지 구성은 유지한다.
- 차단 목록은 로딩·빈 목록·조회 실패·재시도 상태를 제공한다. 해제 성공 후 서버 목록을 다시 조회한다.
- 계정 전환·로그아웃 시 이전 신고 입력을 지우고 진행 중 응답을 현재 계정의 성공으로 표시하지 않는다. 차단 목록도 계정에 따라 다시 조회한다.
- 댓글·답글에는 신고·차단 메뉴를 추가하지 않는다.

디자인 참고: [커뮤니티 · 신고와 차단](https://www.figma.com/design/MYwSnxdhmGZnLuc1pHtjZz/?node-id=1009-6). 마이페이지 예시는 메뉴 배치 참고용이다.

## 서버 연동을 위한 제안 계약

아래 엔드포인트는 이번 브랜치의 프런트엔드 호출 계약이며 **현재 백엔드 구현은 없다**. API 미제공·네트워크 실패·잘못된 응답은 오류로 표시한다. 임시 성공이나 가짜 목록을 실제 앱에 제공하지 않는다.

| 동작 | 요청 | 성공 응답 |
| --- | --- | --- |
| 게시글 신고 | `POST /api/v1/posts/{postId}/reports` | `data.id`, ISO 8601 형식 `data.receivedAt` |
| 차단 목록 | `GET /api/v1/users/me/blocks` | `data.items`: `userId`, `nickname` 배열 |
| 작성자 차단 | `PUT /api/v1/users/me/blocks/{userId}` | HTTP 200 또는 204 |
| 차단 해제 | `DELETE /api/v1/users/me/blocks/{userId}` | HTTP 200 또는 204 |

신고 본문:

```json
{
  "reason": "SPAM",
  "detail": "상세 내용",
  "requestId": "클라이언트가 생성한 요청 식별자"
}
```

`reason` 값: `SPAM`, `ABUSE`, `INAPPROPRIATE`, `PRIVACY`, `OTHER`.

서버는 인증된 사용자 기준으로 처리하고 본인 신고·차단을 거절해야 한다. 클라이언트는 신고자 ID를 본문으로 보내지 않는다. 같은 사용자·`requestId`의 재요청은 기존 접수 결과를 반환하고, 동일 식별자로 다른 내용을 요청하면 충돌로 처리하도록 구현한다. PUT/DELETE는 재요청 가능한 동작이어야 한다.

목록 계약은 현재 전체 목록이다. 서버에서 페이지네이션을 도입하면 커서·추가 로딩을 함께 조정한다. GET 오류를 빈 목록으로 처리하지 않는다.

## 다음 서버 연동 범위

- 신고 DB 저장과 접수번호 반환, 권한·사유·본문 검증, 중복 접수 방지.
- 운영자 이메일 전달 및 실패 재처리. 접수 성공과 이메일 발송 성공을 분리한다.
- 차단 관계 저장·목록·해제 API 및 권한 검증.
- 차단한 작성자의 콘텐츠를 피드·검색·상세·댓글 등에서 어떻게 숨길지 정책을 확정하고 서버 조회에 적용한다. 이번 브랜치는 콘텐츠 필터링을 구현하지 않는다.
- 실제 서버로 저장·재조회·재로그인·네트워크 재시도 검증.

1대1 문의 화면 및 이메일 접수는 별도 작업이다. 이번 브랜치에서 백엔드 변경, 운영 서버 배포, 실기기 검증은 진행하지 않는다.
